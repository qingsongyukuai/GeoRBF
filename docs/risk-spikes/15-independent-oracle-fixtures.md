# Risk spike 15: independent 100-digit oracle fixture pipeline

Issue: [#15](https://github.com/qingsongyukuai/GeoRBF/issues/15)

Evidence seam: T13

Requirements: VAL-001, VAL-002, VAL-013

Probe: [`spikes/oracle-fixtures`](../../spikes/oracle-fixtures/README.md)

## Verdict

**The minimal oracle fixture pipeline succeeds.** A declarative three-case corpus is evaluated by an independent language and mathematical stack at 120 decimal digits, converted to exact hexadecimal `f64`, assigned content-derived stable CaseIds, and emitted with deterministic fixtures and a provenance-rich manifest. A separate consumer validates all identities, hashes, pins, and `f64` round-trips, and a tampered fixture fails deterministically.

The spike is deliberately isolated from the future Rust product tree and has no third-party dependencies. Neither generator nor verifier imports or calls GeoRBF production code, a production backend, LAPACK, Surfe, or another floating-point solver.

These literals are asserted at the public fixture seam rather than recomputed by the test. The general jet uses the determinant-one metric `diag(2,1,0.5)`, while the manufactured case contracts two independently declared scalar functionals.

## Integrity and failure evidence

Each fixture contains:

- a CaseId derived from the canonical declaration;
- canonically sorted declarative input and provenance;
- 110-digit decimal and exact hexadecimal `f64` for every output scalar;
- a result hash and a semantic-content hash.

The manifest additionally records declaration and fixture byte hashes, generator/verifier/lockfile hashes, versions, precision, interpreter, dependency closure, OCI digest, provenance, and output hashes. `verify.py` is a separate consumer: it does not import the generator or recalculate the oracle mathematics. It rejects a changed OCI pin and a one-value fixture tamper with a stable nonzero result.

## Hermetic replay

The T13 suite runs regeneration twice and requires byte-for-byte equality on both passes. `.github/workflows/risk-spike-15.yml` repeats that sequence in two clean boundaries:

1. exact CPython 3.12.3 provisioned from the empty hash-checked lockfile;
2. the checked-out repository mounted read-only into the fixed OCI digest.

Both paths run the independent consumer after regeneration. A local exact-interpreter replay exercises the same test and check commands; the workflow is the durable clean-environment replay contract.

The implementation replay on 2026-08-02 passed in both a newly created dependency-empty CPython 3.12.3 virtual environment and the unpacked read-only Linux x86-64 image selected by the pinned OCI index. The selected platform manifest was `sha256:fd3817f3a855f6c2ada16ac9468e5ee93e361005bd226fd5a5ee1a504e038c84`. Both fresh boundaries ran the behavior suite, regenerated twice with zero byte differences, and passed the independent verifier.

## Proven capability versus unfrozen scope

Proven by this spike:

- an auditable boundary independent of GeoRBF production code;
- at-least-100-digit deterministic evaluation and exact `f64` serialization;
- stable declaration-derived identities, canonical inputs, provenance, and layered hashes;
- byte-identical regeneration and independent consumption;
- deterministic detection of environment-pin and fixture tampering.

Not frozen or admitted by this spike:

- the complete four-kernel origin/cutoff/jet/covariance corpus;
- the complete Cubic CPD, polynomial-mode, KKT/QP/SOCP, recovery, and diagnostic corpus;
- NumericalPolicy, tolerance, ValidationProfile, release corpus, or supersession history;
- any production dependency, API, implementation, backend, or fixture-adoption decision.

The technical hypothesis in #15 therefore succeeds for the minimal pipeline. Completing the ticket does not by itself adopt these sample fixtures as production correctness authority or release the separate gates governed by the other risk spikes and the v1 specification.
